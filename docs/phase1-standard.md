# 一阶段交付标准（2026-11-09 第一版）

一阶段交付 = **同一个提交、同一组开关，连续三局「合格局」**。达标时记下提交号和三局批次号，写进本文末尾的「达标记录」。

这份标准替换睡眠流程第二版里「全局零错误」的口径：把错误分成会归零的「操作错误」和只记录的「策略次优」，并要求三局跑同一份代码。

## 一、范围

| 项 | 一阶段内 | 不在一阶段内 |
|---|---|---|
| 平台 | macOS（Apple Silicon）+ hguandl 分支 PlayCover，`HIRO_DEVICE=maatools` | quartz、ADB、MuMu、雷电、DMM |
| 模式 | H.I.F 本战，VEIL 批量路线（`tools/batch_hif.py`，`watch --auto`） | 选拔、`run_hif` 单局路线 |
| 偶像 / 回忆 | [VEIL] 秦谷美鈴（`i_card-skin-hmsz-3-016`），回忆 `veil-deck2` | 其他偶像、其他牌组 |
| 一局的起止 | 首页 `begin` → R2 结算 `settle` 成功（`"command": "settle", "ok": true`） | 开局前的编成、补 AP |
| 开关 | 测试开关清单里的固定一组（见下文「四」） | 默认关、还没单独验证过的新开关 |

## 二、合格局

一局要**同时**满足 A、B、C 才算合格。

### A. 操作零错误（任何一条不满足 → 不合格，计数归零）

- 没有任何人工介入：手点屏幕、`ledger-edit`、`auto-resolve`、手动续跑命令、重启 watch，代理做的也算。
- 日志里没有 `"ok": false`（exam / settle / auto / prep）、`ResumeBlocked`、`prep 失败`、`Traceback`。
- 没有停下来等人的 `hold`（watch 自己恢复的正常停点不算）。
- 没有撤回出牌（`veil_play_undone`）。
- 看门狗没停机（3 分钟没进展）。
- 底线拦截被触发也算不合格，即使拦得对：比如ジュエル框、破棄、リタイア、通信错误、日付変更卡住。拦得对说明程序没走错，但这一局还是要人处理。

### B. 结果

- R1、R2 都是第 1（優勝），没有用到再挑戦。
- 分数只记录，不设门槛。参考：最近 R1 在 86–93 万，R2 在 103–157 万。

### C. 复盘全对（任何一条不满足 → 不合格，计数归零）

局后对本局的 trace 跑：

| 工具 | 要求 |
|---|---|
| `tools/audit/trace_trust.py traces/batch-<批次>-*-exam*` | 两轮都 `trusted=true` |
| `tools/audit/pitem_replay.py <trace>` | 夜空计数每帧对上画面 |
| `tools/audit/pile_replay.py <trace>` | 整场没有位置不明的牌 |
| `tools/audit/ledger_check.py <批次>` | 账本、回忆全部对上主数据 |
| `tools/audit/landing_replay.py <trace>` | 落地判定和实际一致 |

### 策略次优：只记录，不归零

出牌、买卖、饮料的选择不够好，但没有引起 A 里的任何一条，也没让 B 失败，就记为「策略次优」。

- 记进 TODO.md 本批次一节，标 `[S]`。
- 不影响合格判定，也不在计数中途修。等三连达标或计数已经归零时再统一修。
- 例子：1-q 剩 2 全力过渡没打教えてあげる+（OD 生成眠気打断规划）。按本标准，1-q 是合格局，这个问题记 `[S]`。
- **循环没进去**：先查原因。识别或记账读错导致的，算 A 类错误；出牌选择导致的，记 `[S]`。

## 三、计数规则

1. 连续三局合格 → 达标。任何一局不合格 → 归零。
2. **三局必须是同一个提交、同一组开关**。中途改了影响实机行为的代码（`src/`、`tools/batch_*.py`、`conf/`）或改了开关，计数从 0 重新数。只改文档、测试、审计工具不归零。
3. 开局时工作区必须干净（已提交）。不干净的局作废：不计数，也不归零。
4. 游戏掉线、登录、验证码、新条款这类不归程序管的中断，这一局作废：不计数，也不归零。改过代码时照第 2 条处理。

## 四、开局前的门槛（每次改完代码、开下一局之前）

1. `PYTHONPATH=src pytest -q` 全过。
2. 离线回放不退步：在已有 VEIL trace 上跑 `pitem_replay.py`、`pile_replay.py`、`landing_replay.py`，结果不比上一个提交差。
3. 开关只用测试开关清单里的那一组。新开关（`VEIL_FULL_PLAN`、`VEIL_ENCHANT_RUNTIME`、`VEIL_SIM_UNIFIED`、`VEIL_FP_PLAY_STANCE`、`VEIL_DRAW_PROB` 等）一次只加一个，加之前先在全部 VEIL trace 上离线回放，看它改了哪些步。
   - 连续合格数 > 0 时：要先单独开一局验证。验证局不计数；验证过、决定加进开关组之后，按第三节第 2 条从 0 数。
   - 连续合格数 = 0 时：没有连胜可断，可以直接加进开关组，这一局照常计数。
4. 提交，记下提交号，写进本批次一节。

## 五、错误族：修根源，不补特例

睡眠流程第一、二版里，同一类错会换个样子反复出现。出牌落地判定前后修了 7 次（1-g、1-i、1-j、1-l、1-m、1-p 都是在旧判据上补特例，直到 `HIRO_LANDING_ART` 按卡图认牌、778 对离线全对才算解决）。牌库一览修了 4 次，幽灵牌出现了 3 次。下面四条用来避免这种情况。

1. **每个 A 类错误先归族**，在 TODO 里标族名，例如 `[落地判定]`。现有的族有：落地判定、牌库一览、牌堆记账、页面识别、弹窗时机、读档位点按。新错误不属于这些族就开一个新族。
2. **同一族第二次出错，就不再补特例**：要么重做这一层的判据，要么把修法在全部 VEIL trace 上回放，列出对错数（像 `landing_replay.py` 那张 778 对的表）。只拿出错那几帧验证不算修完。
3. **新阈值要在全量 trace 上验证**：报告里写清误判、漏判各几次，以及样本数。只靠 2–3 个样本定下来的阈值不能进计数局。
4. **每局按族统计错误数**，写进本批次一节。各族数量稳定下来、不再冒出新族，才说明长尾在收敛。这个统计比单看连胜更早看出离达标还有多远。

## 六、每局记录

写进 TODO.md 本批次一节：

- 提交号、开关组（与上一局相同就写「同上」）
- 用时：`begin` → `settle` ok 的墙钟时间，以及 R1、R2 各自的用时
- 分数、名次
- A 类错误（有就写族名、现象、seq / 帧、推测原因；同族第二次的写清是重做判据还是全量回放）
- C 类复盘结果
- `[S]` 策略次优
- 本局各族错误数
- 结论：合格 / 不合格 / 作废，以及当前连续合格数
