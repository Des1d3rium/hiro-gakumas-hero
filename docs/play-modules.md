# 出牌逻辑模块化方案（VEIL → 通用循环流派）

2026-11-09 检查 `src/hiro/brain/veil.py`（1,400 行）和 `src/hiro/produce/veil_exam.py`（2,290 行）后写。
前提（使用者）：「循环状态」可以推广到别的职业 / 偶像。下面先说现在的逻辑怎么走、哪些地方写死了 VEIL，再给拆分方案和迁移顺序。

## 一、现在的出牌逻辑

`VeilAdvisor.decide` 一个函数大约 600 行，从上往下按条件依次返回，没有显式的阶段：

| 顺序 | 分支 | 代码位置 | 做什么 |
|---|---|---|---|
| 0 | 守门 | 793–810 | 只认 R1 / R2；分数超过 `LIMITS` 就 Skip |
| 1 | 读局面 | 812–836 | 手牌、按名字索引、全力値闸、饮料、姿态、夜空、次数、本回合已打；判定是否进入循环 |
| 2 | 循环前喝ソーダ | 838–841 | 只差 1–2 张核心牌时喝 |
| 3 | 最后一回合喝初星湯 | 844–847 | |
| 4 | 全力过渡 | 848–869 | 循环里全力値满 10、进了全力：手写两套顺序（按夜空 1 / 2） |
| 5 | **五卡循环** | 870–926 | 先喝饮料，再按 `ORDERS[夜空]` 打 4 张核心牌，最后补第五张；アイドルになります+ 例外先打 |
| 6 | **进循环规划** | 928–937 | `plan_cycle`：枚举本回合出牌顺序，找出能让下回合开局进入循环的那一种 |
| 7 | **过渡** | 949–1059 | 牌库已经压缩完：need_flower / need_draw / need_warm 三个需求，加上清掉一次性牌、OD 攒全力値等手写规则 |
| 8 | **清牌** | 1061–1399 | 姿态限定牌 → 攒全力値 → 体力闸 → 全力値预留 / 封顶 → 按优先级排序 → 枚举出牌顺序 → 抽牌、ホエイ、ソーダ的各种例外 |

决策依赖的「打出这张牌之后局面怎么变」，分散在 veil.py 的辅助函数里：`after_play`、`hp_loss`、`fp_delta`、`destination`、
`next_stance`、`start_turn`、`warm_next_turn`、`swaps_hand`。记账（`VeilBrain._commit`、`track_piles`、`track_full_power`、
`piles.py`）又在 veil_exam.py 里各自推一遍。

## 二、检查发现的问题

1. **同一套机制推演写了四五遍。** 「打一张牌之后出牌次数怎么变」至少出现在 `plan_cycle.run`、`gains_now`、`gain_at`、`gains_at`、
   `cycle_reachable`、`VeilBrain._commit`（`actions_left += 1`）这几处。另外，「温存切到強気加 1 次」在有的地方受 `release_gain()` 控制，
   有的地方不受。三处全排列搜索（进循环规划、清牌顺序、`cycle_reachable`）各自的推演细节也不一样：
   有的算体力、有的不算，有的算手牌溢出、有的不算，有的看 `next_stance`、有的不看。改一处忘了改另一处，就会出现「规划说能进循环，实际打出来进不去」这类问题。
2. **卡牌、饮料、道具都按名字写死。** 写死的包括：核心牌 `CORE`、四张牌在循环里的位置（OD、教えて、巻き返し、エンタ）、`ORDERS`、
   アイドルになります 的三选二条件、ひと呼吸 要后打、ガタゴトすやすや / 一心不乱 的姿态要求、四种饮料 `WHEY/SODA/BOOST/EXTRA_TURN`、一番星、
   `FP_RESERVE_AT=3`、`LIMITS`。其中很多信息主数据里已经有了：使用条件、全力値消費、姿态要求、再动、抽牌、饮料效果。
   这些都已经结构化（`card_fx`、`pitems`），只是 decide 还没改成用它们（账本那一侧已经在用：夜空计数、一番星按 `pitems` 推）。
3. **开关太多，默认值和实际跑的配置对不上。** 现在一共 27 个开关，15 个默认开。睡眠流程的启动脚本另外又打开了 11 个默认关的开关
   （CYCLE_PLAN、IDOL_CLEAR、STRONG_TEACH、CYCLE_WHEY、DRIVE_CHECK、STANCE_LATER、HP_ZERO、STANCE_SCREEN、CYCLE_TAP、IDOL_FP_GATE、STANCE_UNLOCK）。
   结果是：实机验证过的配置不是代码的默认配置，代码里还留着两套逻辑分支。
4. **执行层靠读决策理由的文字来判断。** `exec/cycle_tap.py` 要看理由里有没有「五卡循环」几个字，才决定要不要连打。改一个理由文案，连打功能就会悄悄失效。
5. **出牌顺序只验证了「打不打得出」，没有比较「得分好不好」。** 见下一节的实验。

## 三、实验：循环顺序能不能从主数据自动推出来

用 1-o 那一局 trace 里的 4 张核心牌（带主数据结构化效果），在现有的 `after_play` 上枚举 24 种出牌顺序。
筛选条件只有一个：**下回合开局又回到同一个状态**，也就是 ① 开局姿态是温存或のんびり（算上「次のターン温存」这类预约），② 夜空剩余次数和本回合开局一样。

| 开局夜空 | 能回到同一状态的顺序 | 打完还剩 1 次（能接第五张） | 现在写死的 `ORDERS` |
|---|---|---|---|
| 1 | 12 种 | 4 种 | OD → 教えて → 巻き返し → エンタ（在这 4 种里） |
| 2 | 6 种 | 2 种 | OD → 巻き返し → 教えて → エンタ（在这 2 种里） |

结论：

- **「循环」可以定义成一个通用概念：** 牌库压缩到一组复用牌，而且存在一个出牌顺序，打完之后下回合开局状态（姿态、P 道具计数、出牌次数、抽牌数）和本回合开局一样。
  这件事只需要一个能正确模拟回合的推演器就能自动搜出来，不需要知道偶像是谁。
- **但光看能不能打完，选不出唯一的顺序。** 剩下几种顺序之间的取舍靠的是得分：エンターテイナー 放在夜空触发之后（熱意+40%）、OD 先打攒全力値给巻き返し 用。
  所以选顺序还需要一个**可替换的打分器**。开源版可以先用「得分牌放在加成之后」这类社区规则，私有插件可以换成价值表或模拟器。

## 四、拆分方案

```
          ┌────────────── 偶像配置 profile（conf/，前端可编辑）──────────────┐
          │ 循环牌组 / 第五张规则 / P 道具 id / 停手阈值 / 打分规则 / 保底线      │
          └───────────────┬──────────────────────────────┬────────────────┘
                          ▼                              ▼
牌库视图 deckview ──► 阶段判定 phase ──► 策略（cycle / transition / clear）──► 决策
   ▲  （账本：piles.py）      │                 │   ▲
   │                         ▼                 ▼   │
   │                 约束 guards ◄──── 序列搜索 planner（一个搜索，换目标函数）
   │                         ▲                 │
   └──── 记账 commit ◄── 回合推演器 sim（唯一的「打出去之后会怎样」）◄── card_fx / pitems（主数据）
```

| 模块 | 职责 | 来源（现在的代码） | 和 VEIL 有关的东西放哪里 |
|---|---|---|---|
| `play/sim.py` 回合推演器 | `TurnState`（姿态 + 段階、预约姿态、出牌次数、再动层数、全力値、体力、元気、手牌数、P 道具计数、附魔），`step(state, card \| drink)` 返回新状态。是唯一的推演实现，决策、记账、回放审计都调它 | `after_play`、`hp_loss`、`fp_delta`、`start_turn`、`gains_*`、`_commit` 里推演的那部分 | 不放。夜空、一番星都通过 `pitems` 的计数器和附魔表达 |
| `play/deckview.py` 牌库视图 | 从账本得出每张牌在哪、哪些是一次性、哪些存疑、下回合抽几张；回答「牌库是否已经压缩成循环牌组 + 最多 k 张可清的牌」 | `small_deck`、`plan_cycle` 前半段 | 不放 |
| `play/cycle.py` 循环 | ① 求解：在 sim 上搜出所有回到同一开局状态的顺序，再用打分器排序，按开局状态分别缓存；② 执行：按顺序打，处理开局饮料和第五张 | `ORDERS`、循环分支（870–926） | 只放 profile 里的循环牌组；`ORDERS` 退化成求解结果的校验用例 |
| `play/planner.py` 序列搜索 | 一个带剪枝的全排列搜索（手牌 + 饮料，sim 推演），目标函数可替换 | `plan_cycle`、清牌里的 `run`、`cycle_reachable` | 不放 |
| `play/phase.py` 阶段判定 | 清牌 → 过渡 → 循环 → 恢复（全力、断循环）→ 收尾（最后一回合、停手阈值） | decide 里分散的 `compact` / `cycle` / `full` 判断 | 不放 |
| `play/guards.py` 约束 | 体力闸（保底线、净体力）、全力値预留 / 封顶、手牌溢出、使用条件（主数据 `play_condition`：三选二、姿态限定）。每条返回「允许 / 不允许 + 原因」 | `affordable`、`keeps_reserve`、`under_cap`、`idol_starved` 等 | 保底线和 `MINOR_LOSS` 放 profile；全力値预留值改成从剩下的牌里取最大的「全力値消費」 |
| `play/resources.py` 饮料 | 按饮料效果分类（+出牌次数、抽牌、加成、加回合），决定喝的时机 | 四个写死的饮料名和对应分支 | 不放 |
| `play/objectives.py` 打分 | 目标函数：清牌 =（清掉的一次性牌数，剩余次数，……）；过渡 =（下回合能进循环，……）；循环 = 得分规则 | `priority`、`run` 的返回元组、`plan_cycle` 的打分 | 打分规则放 profile；可以通过插件换成私有价值表 |
| `play/profile.py` 偶像配置 | 读 `conf/play/<idol>.json` | `IDOL`、`CORE`、`LIMITS`、阈值常量 | 这里就是 VEIL 的配置 |

拆完之后，`VeilAdvisor` 只剩一行：`CycleAdvisor(profile("i_card-skin-hmsz-3-016"))`。
执行层改看 `Decision` 上的显式字段（例如 `phase="cycle"`），不再读理由文字。
这个方案和 TODO.md 里「策略配置化 + 前端」的方向一致：前端可以直接编辑 profile。

## 五、迁移顺序

每一步都放在开关后面、默认关，用 31 份 11-09 的 trace 回放验证完再打开（AGENTS.md 第六节）。

1. **sim 对齐**：新写 `sim.py`，让它在 31 份 trace 上逐帧复现现有推演，包括姿态、夜空、全力値、出牌次数、体力；
   并用 `pitem_replay` 和 `pile_replay` 做同样的画面核对。全部对齐之后，veil.py 的辅助函数改成调 sim。
2. **循环求解**：`cycle.solve(profile)` 输出的结果要包含现在的 `ORDERS`。如果打分器排出的第一名和 `ORDERS` 不一致，把差异列出来交给使用者裁定。
3. **统一搜索**：清牌、过渡、进循环规划三处换成同一个 planner。逐帧比较新旧决策，输出差异报告；差异逐条确认后再切换。
4. **约束和饮料改用主数据**：去掉按名字判断的写法，例如三选二改成用 `play_condition`。
5. **抽出 profile，清理开关**：实机一直开着的 11 个开关改成默认开；已经被替代的分支删掉。
6. **第二个偶像**：拿一位循环流派的偶像只写 profile，看循环求解能不能直接用。

注意：睡眠流程正在实机跑（1-p），而且上面所有改动都没提交。重构应该先提交现有改动，再新开分支或 worktree 去做，不要动正在跑的那份代码。
